# 010 — The skill library: one layout for every kind, and subagents that use it

**Status:** open, 2026-11-09. Opened by the design seat on the person's words (`../../docs/ideas/20261109.md`: "스킬들을 소스코드로 만들고, LLM이 필요한 스킬들을 가져다 사용", then the kinds and "서브에이전트들이 활용"), recorded in plan.md 14-30 and 14-31. Comes after `009` and before `007`, which writes the first kind (bounds) on what this task lays down.

**Seat:** the manifest schema, check 22, bundle check B11, their rejected fixtures and one accepted example skill per kind are the design seat's and land first. The catalogue, the runner, the template's subagent part and the first skills are a `meta-…` seat's (self-registered under the standing rule of 2026-11-09, or seated by the person).

**Goal:** a skill is a folder of source code that a model can find, choose and run, and that a check can judge. Every kind shares one layout and one manifest; the Meta-Agent writes skills as it builds; a bundle receives the skills its specification names and its subagents use them. One skill of each named kind exists on fixtures at the end: a bound, a hardware connection, a hardware boot sequence, a hardware control and a hardware calibration (all against a mock, `held`), a hardware situation-awareness and a data analysis skill.

**What is settled (the person, 2026-11-09):** skills are source code; the model takes the ones it needs; the kinds named are hardware connection, hardware boot sequence, hardware control, hardware situation awareness, hardware calibration, data analysis and parameter bounds, the list open; whether a device calibrates itself is checked, and a calibration that needs outside help is designed with the person; the skills are made by the building; subagents use them. MP1 stands: the Meta-Agent makes a hardware skill and never runs it on a device.

**Method (recommended, not settled):**
- Design seat, the manifest: `contracts/schemas/skill.schema.json` for `skill.json`: `id`, `version`, `kind` (`bound | hardware_connection | hardware_boot | hardware_state | hardware_control | hardware_calibration | data_analysis`, a vocabulary file so that a new kind is one line and the person's "등" stays open), `side_effect: none | read_device | write_device`, `applies_to {methods[], instruments[], engines[], parameters[]}`, `inputs[]` and `outputs[]` as `{name, unit, meaning}`, `calls_tools[]` (required unless `side_effect` is `none`), `entry` (the script and function), `source` (what the skill rests on, with a locus), `cases` (the file), and for `hardware_boot` a `steps[]` list of `{n, actor: device | person, precondition, action, verify}` whose preconditions and verifications name readings of a `hardware_state` skill. The folder is `<kind>/<id>@v<N>/` with `SKILL.md` (frontmatter `name`, `description`; body: what it does, when it applies, what it needs, what it returns, what it never does), `skill.json`, `scripts/`, `cases.json`.
- Design seat, calibration: `tool_profile.schema.json` gains `self_calibration[]`, one claim per quantity `{quantity, kind: observed | derived | inferred | unknown, mode: self | assisted | unknown, evidence, requires}` under the rules every claim already has (check 11); a new card `calibration_design` (`quantity`, `reference` with its traceability, `steps[]` of `{actor: person | device, action, reading, recorded_as}`, `interval`, `acceptance` as a threshold that is `null` or `author: human`, `status: draft` until `confirmed_by: human`), with an accepted example and rejected fixtures (an acceptance limit written by a seat; a design confirmed by a seat).
- Design seat, check 22 (skills): the folder is complete and the manifest valid; `SKILL.md`'s name and the folder's id agree; a version folder present at `HEAD` is unchanged (append-only); the entry function exists; the source is read with `ast`: a `side_effect: none` skill imports `math`, `statistics`, `json` and its own siblings only and opens nothing; no skill of any kind imports `socket`, `serial`, `subprocess`, `ctypes`, `requests` or a vendor package, since a device is reached through `calls_tools` only; no numeric literal is compared against an input in a device skill (a limit belongs to `envelope/safety.json`); every case in `cases.json` runs and gives its stated output (for device skills against the recorded mock transcript the case names); a `write_device` skill has `status: held` unless a `persons_words` reference releases it; a `hardware_boot` skill's steps are numbered without a gap, every step has a `verify`, a `person` step calls no tool, and its last step's verification is the `ready` verdict of a `hardware_state` skill. Rejected fixtures, one per assertion. Bundle check B11: every skill a subagent or `CLAUDE.md` names exists in the bundle's `skills/`; a subagent's `side_effects` cover the skills it names; at most the subagents the specification marks may name a `write_device` skill; B8 and B9 still hold.
- Meta seat, catalogue and runner: `src/skills/catalogue.py` builds `skills/index.json` from the manifests (never by hand) and answers `python -m meta_agent.src.skills list [--kind K] [--parameter P] [--instrument I]` with each skill's id, one-line description and inputs, which is what a model reads to choose; `python -m meta_agent.src.skills run <id@vN> --inputs <file>` loads the entry function, checks inputs and outputs against the manifest, and for a device skill routes every call through a tool runner it is given (the bundle's `run_tool.py`, or the mock runner here) and refuses when none is given. The runner writes what it ran (skill, version, inputs, outputs, the tool calls and their verdicts) as a file a card can cite.
- Meta seat, the bundle: at S5 `src/build/bundle.py` copies the skills the `agent_spec` names into the bundle's `skills/` unchanged, with their manifests, and writes `.claude/agents/<name>.md` for the subagents the specification names, each listing its skills and side effects; `CLAUDE.md` gets the trigger sentence B8 asks for. Recommended first drawing, by side effect: `reader` (connection, situation awareness), `operator` (boot sequence, calibration and control; the only one that may name `write_device`; starts no action without the gate's pass), `analyst` (analysis, bounds). The drawing is on the `agent_spec` where the person sees it; `template_v1` becomes a new template version, the old one kept.
- Meta seat, the first skills, on fixtures and a mock only: `bound/shear_rate_max_from_max_speed@v1` (shared with `007`), `hardware_connection/find_and_identify@v1` (lists what answers, reads the identity, opens and closes a session; no setting written), `hardware_boot/bring_to_ready@v1` (the fixture profile's start-up order as steps: the person's steps first and waited for, then initialise, home, set temperature, each verified by a reading; a failed verification stops there and returns the state; `status: held`, bench cases `not_run: requires bench`), `hardware_calibration/calibrate@v1` (reads the profile's `self_calibration` claim for the quantity and takes one way: `self`, the device's routine as gated tool calls, returning a `calibration:<id>` number with its expiry; `assisted`, no tool call, a `calibration_design` draft with the questions for the person left open in it; `unknown`, a gap naming what would settle it; `status: held`, bench cases `not_run: requires bench`), `hardware_state/read_status@v1` (state, temperatures, positions, error flags as `measured` readings with time and run id, and a plain verdict `ready | busy | fault | unknown` whose rule is in the skill and whose inputs are the readings), `hardware_control/run_steady_shear@v1` (a procedure of tool calls: check state, set, start, poll, stop; every call through the gate; `status: held`, bench cases `not_run: requires bench`), `data_analysis/flow_curve_fit@v1` (a power-law fit of stress against rate on a fixture file, returning `computed` numbers with `basis` and the residual). The mock is a recorded transcript under `tests/fixtures/`, written by hand from the fixture profile, never from a device.
- Tests: the catalogue lists seven skills and a second build of it is identical; each skill's cases pass through the runner; the control and boot skills run without a tool runner are refused, and run on the mock with a failing gate make no tool call after the gate; the boot skill on a mock whose second verification fails stops at that step and reports it, and with a `person` step unanswered it waits and calls nothing; the calibration skill on a profile claiming `self` returns a calibration number with an expiry, on `assisted` writes a `calibration_design` draft and makes no tool call, on `unknown` returns a gap; an echo-like fixture build whose specification names two skills and one subagent passes B1–B11; `--expect-fail` rejects every new fixture.
