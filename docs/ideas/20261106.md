## The Meta-Agent fetches the tools a request needs by itself

> 필요할 때 스스로 다운받으면 좋을듯

[It would be good if it downloaded them by itself when they are needed.]

Said right after plan.md 14-22(d) gained Ghidra and a .NET decompiler (ILSpy) on 2026-11-05 (`docs/ideas/20261105.md`), in answer to the note that, like the other tools there, they enter `tools.lock.json` only when a request needs them and that nothing is installed now. "Them" are the external tools S2 and capture files need: Ghidra with its JDK, ILSpy, Frida's native module, TShark and capinfos, sigrok-cli.

What the person's words settle: when a request needs an external tool this computer lacks, the Meta-Agent fetches and installs it itself through `bootstrap.py` instead of asking the person to run a command. Nothing else about how a tool reaches a computer changes. The tool is pinned in `tools.lock.json` with its version, the project's own source, a checksum from that project's own release, and its license. It lands in the user's tools home outside the repository, is called out of process and is never vendored. `bootstrap.py` touches no PATH, registry or agent configuration; a tool's location is passed in the environment of the call that uses it (for REA's Ghidra provider, `GHIDRA_INSTALL_DIR` and the JDK given to `bootstrap.py run rea`).

What the words do not reach, so it stays the person's step: anything that needs administrator rights or installs a driver or a service (a packet-capture driver such as Npcap or USBPcap, a virtual serial port pair such as com0com), a PATH change, a new WSL distribution, and anything on the instrument computer (P0). Frida's native module is fetched only when an `analysis_permission` covering runtime analysis of that software exists, because runtime capture is its only use.

Not settled, and recommendations only (plan.md 14-23): whether the first pin of a tool not yet in `tools.lock.json` needs the person's yes once (recommended: name, source, version, size and license shown once per tool, after which every computer fetches it without asking) or whether the commit of the pin is the only record; whether a project permission rule lets `python bootstrap.py install` run without a prompt in Claude Code (recommended for that one command only, since it installs nothing that is not pinned); a check on `tools.lock.json` (every entry names a version, its own source, a checksum or commit, and a license) with its rejected fixture, landing with the first new pin; and installers for Ghidra, a JDK and ILSpy, built when the first real target needs them (MP8).

## The first pin of a new tool needs no yes

Asked how a tool not yet in `tools.lock.json` is pinned the first time, with two choices, "한 번 확인" [confirm once] (shown as recommended: name, source, version, size and license shown once per tool) and "묻지 않기" [don't ask], the person answered:

> 묻지 않기

[Don't ask.]

What the words settle: the Meta-Agent pins a new tool in `tools.lock.json` and fetches it without asking. The commit of the pin, judged by the gate like any other, is the record, and the report of the request that needed the tool names it (plan.md 14-23(a)). What a pin must carry does not change: version, the project's own source, a checksum or commit from that project's own release, license.

What the words do not reach: a tool that is not open source or whose download asks for terms to be accepted (accepting terms stays the person's), and everything the first section of this file leaves to the person (administrator rights, drivers and services, PATH, new WSL distributions, the instrument computer, Frida's native module without an `analysis_permission`). Because no person looks at a pin before it is used, the check on `tools.lock.json` (plan.md 14-23(c)) is the only thing between a pin and its use; it is still recommended to land with the first new pin. Still open: the project permission rule for `python bootstrap.py install` (14-23(b)).
