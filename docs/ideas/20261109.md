## A change in the way of designing: bound skills as source code, picked by the model

Later the same day, with the standing rule and `tasks/009` written and not yet committed, the person changed how parameters are reasoned about:

> 설계 방식 변경
> 각 파라미터의 최대값 최소값을 계산할 수 있는 다양한 스킬들을 소스코드로 만들고, LLM이 필요한 스킬들을 가져다 사용할 수 있게 하자.

[A change in the way of designing. Let us write, as source code, various skills that can compute the maximum and the minimum of each parameter, and let the LLM take and use the skills it needs.]

What the words settle:

- The unit of parameter reasoning is a **skill written as source code that computes a maximum or a minimum of one parameter**: one physical, numerical or instrument reason per skill, and many of them, of various kinds.
- **The model chooses** which skills a request needs and uses them. The number is still the code's: a skill is run, never imitated, so a bound is `computed` and a model's own figure stays E6 and enters nothing (root `CLAUDE.md`).
- This revises what "Take all six" settled on 2026-11-08 in two places of plan.md 14-26: (b) the helper registry `contracts/registry/helpers.json` with expressions in a small language, and with it the expression evaluator inside the validator of (c), give way to skills as source files; and "a recommendation mode chosen by a deterministic rule, never by the model" no longer covers the choice of which constraints apply, which is now the model's.

How the design seat reads it (recommendations, plan.md 14-30; none of this is the person's word):

- A skill has the layout the bundle already has for skills (plan.md 5.1 S5, `skills/<name>/SKILL.md` + `scripts/`), so a skill a specification used is copied into the bundle unchanged and the built agent's own model can use it when conditions change. What the model reads to choose is `SKILL.md`; what the code reads is a manifest; the computation is one pure function.
- The model picks skills and binds each input to a row of the sheet; a runner executes the skill and writes the bound as a row whose `basis` names the skill, its version and the input rows. The feasible interval is the highest floor and the lowest ceiling, as SMA's S4 intersects; an empty interval names the two skills that collide.
- The recompute check of 14-26(c) stays and gets simpler: the validator re-runs the skill named in `basis`. For that to be safe a skill is pure (standard-library `math` only, no input or output), which a check reads off its source.
- A skill lands with at least one worked case from the source it cites, and a check runs the cases, as a check lands with its rejected fixture. A constant that is a judgement (a Courant limit, "ten particle diameters", a fraction of a relaxation time) is an input row with its own source and grade, never a number inside the skill, so that a threshold stays the person's and the grade of the bound follows the worst input.
- Since the model chooses, an omission must be visible: a skill declares what it applies to, and the sheet lists every skill that applies by declaration as used or as not applied with a reason. Leaving one out silently is what a check refuses.
- A safety-relevant row still gets a value from nothing (check 4); a skill may attach a ceiling as information.
- What stands from 14-26: the grade rule `max(E4, worst input)`, first-order uncertainty, the adapters, and `neighbourhood` and `tradeoff`, which now work inside the interval the skills give.

What the words do not reach: whether the choice of the point inside the interval (the mode) is also the model's, where the recommendation is to leave it to code, since the interval is where the model's judgement was needed; whether a model may write a new skill in the middle of a request, where the recommendation is that it may draft one and that a seat lands it with its worked case before any card uses it; where the catalogue the model reads lives for a Claude Code session, since `.claude/skills/` is the design seat's; and the thresholds of 14-15.

Done by the design seat on these words: plan.md 5.3, 12 (M3), 14-26 (revised) and 14-30; `meta_agent/tasks/007` rewritten around bound skills and renamed. Nothing is built.

## The skill library widens: hardware and analysis skills, used by subagents

While the change above was being written the person added:

> 하드웨어 연결 스킬
> 하드웨어 제어 스킬
> 하드웨어 상황 인식 스킬
> 데이터 분석 스킬
> 등 스킬들을 만들도록 해서 이를 서브에이전트들이 활용할 수 있도록 하자

[A hardware connection skill, a hardware control skill, a hardware situation-awareness skill, a data analysis skill, and so on: let us have such skills made, so that subagents can make use of them.]

What the words settle:

- Skills written as source code are not only for parameter bounds. The library has kinds, four named and the list open ("등"): **hardware connection**, **hardware control**, **hardware situation awareness** (reading what state the hardware is in), **data analysis**; the bound skills of the section above are one more kind.
- **Skills are made**, that is, they are an output of the building: the Meta-Agent writes them as it builds an agent, and they accumulate.
- **Subagents use them.** The users of a skill are subagents, each taking the skills its work needs.

How the design seat reads it (recommendations, plan.md 14-31; none of this is the person's word):

- The subagents are the built agent's own, `.claude/agents/<name>.md` in the bundle, which plan.md 5.1 already lists as a part of the bundle and the template does not have yet. A subagent is not a seat and not a second agent: it writes nothing to the record, the agent's seat commits, and "one agent only" (2026-10-29) stands. The Meta-Agent's own sessions use the same library where it applies to them (bounds, analysis).
- MP1 and Tier 0 are untouched: the Meta-Agent makes a hardware skill and never runs it against a device. Here a hardware skill is proved against a mock, and its bench tasks are `not_run: requires bench`.
- Every skill states its side effect, `none | read_device | write_device`. A skill reaches a device only through the bundle's gated tool path (`src/run_tool.py`: gate, input check, adapter, output check, error contract), so the order SMA's operator keeps (safety loaded, plan authorised, lock, limits) is kept and no skill carries a limit value. A `write_device` skill goes to `held[]` until the analysis permission, the person's safety values and the person's approval exist, as S4 already rules for any unresolved side effect.
- What each kind returns is already in the vocabulary: connection, the device's identity as `observed` claims; situation awareness, the device's own readings as `measured`; analysis and bounds, `computed` numbers whose `basis` names the skill and its inputs so that they can be recomputed.
- A subagent's definition names the side effects it may use; one way to draw them is by side effect, not by kind: one that only reads (connection, situation awareness), one that alone may write (control), one that touches no device (analysis, bounds).

What the words do not reach: which subagents a bundle has and whether the Designer derives them or the template fixes them; whether hardware skills are written per instrument or per protocol; who lands a skill the model drafts; and everything plan.md 9 keeps human-only, above all safety values and the approval of a hardware action.

While `tasks/010` was being written the person added one more kind:

> 하드웨어 부팅 시퀀스 스킬도 하나 넣고

[And put in a hardware boot sequence skill as well.]

What the words settle: a fifth named kind, the **hardware boot sequence**: the ordered steps that bring an instrument from off to ready. How the design seat reads it: a boot sequence is an ordered list of steps, each with a precondition read through a situation-awareness skill and a check that it took effect; some steps are a person's hands (air supply, a transport lock, a geometry mounted) and are marked so, the skill waiting for the person's word rather than assuming; it writes to the device, so it is `write_device`, `held` and mock-only here like control; and it ends by handing the state to situation awareness, whose verdict `ready` is the only thing that says the boot succeeded.

Done by the design seat on these words: plan.md 14-31, and `meta_agent/tasks/010` for the layout, the manifest, the check and the subagent part of the template that every kind shares; `tasks/007` builds the bound kind on it. Nothing is built.

## A calibration skill, and a design made with the person when calibration needs outside help

Next the person added calibration:

> 하드웨어를 스스로 캘리브레이션 할 수 있는 디바이스인지 확인하고 캘리브레이션 스킬도 넣자.
> 만약 외부 조력이 필요한 캘리브레이션이라면 사용자와 설계를 구상하도록 하게해

[Check whether the hardware is a device that can calibrate itself, and let us put in a calibration skill too. If it is a calibration that needs outside help, have it work out a design together with the user.]

What the words settle:

- Whether a device **can calibrate itself is checked**, not assumed. It is a claim about the tool like any other: `observed | derived | inferred | unknown` on the `tool_profile` (S2), per quantity, and `unknown` is asked or is a gap.
- **Calibration is a kind of skill**, the sixth hardware-side kind named.
- When calibration **needs outside help** (a reference material, a standard weight or geometry, a second instrument, a technician, the person's hands), the agent does not run anything: it **works the calibration design out with the person**.

How the design seat reads it (recommendations, plan.md 14-31(l)): the skill's first step reads the profile's claim and takes one of three ways. `self`: the device's own routine is run as a procedure of gated tool calls, like a boot sequence, `write_device` and `held`, mock only here; what it returns is a `calibration:<id>` number, graded E2, whose expiry is mandatory (plan.md 6.3). `assisted`: no tool call; a design conversation with the person whose result is a card, a calibration design: which quantity, against what reference and its traceability, whose hands do which step, what is read and how it is recorded (`operator_read`), how often, and the acceptance limit, which is a threshold and so the person's; the agent proposes, the person decides, and the card is `draft` until the person confirms. `unknown`: a gap that names what would settle it. A number measured on an uncalibrated or expired quantity says so on its row.

## What two seats in one folder showed (a finding of `tasks/009` part 7, not the person's words)

Read off runs on the MacBook Air on 2026-11-09, at `17ea397`, with the design seat acting once as the seat that leaves work unfinished and once as the seat beside it.

- With a clean tree the edit hook's command, `python contracts/validate.py --quiet`, exits 0.
- Seat A leaves a card cut off in the middle of a write (`meta_agent/requests/req-halfway/agent_goal.json`, malformed JSON, never staged). The same command now exits 1 with `failed_checks=[1]`, so **every edit seat B makes is answered by the hook with A's failure** (`.claude/settings.json` turns the exit into 2).
- With the same file well-formed but unfinished (two fields), the command exits 1 with six failures of check 1.
- Seat B then commits one path of its own, `docs/probe-009-7.md`, with `seat_commit.py`. **The commit is refused**: the pre-commit hook's `validate.py --staged` judges the whole working tree, A's untracked card included, before it looks at the index. `no commit was made`.
- What does hold (`contracts/tests/test_seat_commit.py`, in a temporary repository with the real hook): with A's file staged and another unstaged, B's commit carries only B's path and B's committer, A's staged file stays staged, and the repository's `committer.name` is never set.

So several seats can share the folder and the index, but not yet the gate: one seat's unfinished card stops every other seat's commit until it is finished or removed. The design seat's recommendation, for the person since it narrows what a gate judges at one moment: at commit time the validator judges **the tree the commit would make** (the index git builds for the commit, exported to a temporary folder), not the files other seats have lying in the working copy; CI judges every pushed tree in full, and a seat's own unfinished card still stops its own commit, because it is in it. The edit hook is the same question for `.claude/settings.json`, a standing configuration and so the person's: judge the files the seat itself changed, or keep the whole tree and accept the noise. Until the person decides, a seat writes a card whole or keeps its draft outside the repository.

## The commit gate judges the tree the commit would make

The finding above was put to the person as one question, "Shall the commit gate judge only the tree the commit would make?", with the recommendation to change it. The person answered:

> Yes, change it

What the words settle: at commit time the validator judges the tree the commit would make, not the files other seats have lying in the working copy. This narrows what the pre-commit gate looks at at that moment, so it needed the person's word (plan.md 5.5, the ratchet) and now has it.

How the design seat does it: `validate.py --staged` exports the index git has built for the commit to a temporary folder and runs the validator **from that folder**, so the cards, the schemas, the vocabularies, the seat table and the validator's own code are the commit's, and another seat's unfinished card, half-edited schema or half-edited validator in the working copy cannot stop or bend the judgement; the git questions (the index's paths, the committer, the history) are still asked of the real repository. What does not change: every check still runs, a seat's own unfinished card still stops its own commit because it is in it, and CI judges every pushed tree and the whole history in full. `meta_agent/wiki/` is not in git and so is not judged at commit time; a plain `python contracts/validate.py` judges it as before.

What the words do not reach: the edit hook in `.claude/settings.json`, which still judges the whole working tree after every edit and so still answers one seat's edit with another seat's failure. It is a standing configuration and stays the person's; the recommendation of plan.md 14-29(f) for it stands.
