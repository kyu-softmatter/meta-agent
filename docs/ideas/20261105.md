- Published benchmarks where dedicated agents lead were run mostly on computer-science papers.
- Full text: the open tools reach open-access copies only; a subscription paper reaches an agent only through a person's own download. The person's words settle the direction: no dedicated paper-search project is adopted; searching stays with Claude Code. The form is a recommendation and is not confirmed:

1. The search runs on a scholarly index (OpenAlex, with Semantic Scholar as a second source), keyword search plus one hop of citation expansion, and Claude reads and selects; general web search is a supplement.
2. Open-access full text is fetched only from the indexes' open links; a subscription paper enters only when the person downloads it and drops it into `meta_agent/inbox/materials/drop/`, and `may_quote` is the person's word. 3. API keys for OpenAlex or Semantic Scholar, if wanted, are requested by the person; the anonymous budgets ran out during the comparison.
4. Whether licensed full text may be read by Claude at all is a question for Stanford Libraries before any paywalled PDF is given to an agent.

## S2 reads the software to be made into an agent through REA, on six points

> S2에서는 REA를 이용해 에이전트화 하고자 하는 소프트웨어를 분석할거야.
> 연결방식, 작동방식, 주요 파라미터, 대역폭, 실시간 정보, 업데이트 주기 등

[In S2 we will use REA to analyse the software we want to make into an agent: its connection method, how it operates, its main parameters, bandwidth, real-time information, update cycle, and so on.]

What the person's words settle: S2 (Tool Understanding, plan.md 5.1) analyses the binary and runtime of the software to be made into an agent with REA, and its `tool_profile` answers six points, each as `claims[]` items whose `capability` names the point: `connection` (transport and protocol between the software and the instrument or engine: TCP/UDP, serial, USB, VISA/GPIB, named pipe, file exchange, vendor SDK), `operation` (the command sequence and states: connect, configure, start, acquire, stop, export), `parameter` (the settable parameters with their units and valid ranges), `bandwidth` (bytes per second and message sizes on that link), `realtime` (which quantities are streamed live while a run is in progress), `update_rate` (how often those quantities are refreshed). "Update cycle" is read here as the data refresh period, not the vendor's release cycle; the person may say otherwise.

What does not change: binary and runtime analysis still needs an `analysis_permission` that names a person, a scope, a basis and a date for that software (check 11); without it the six points are `gaps` with reason `permission_required` and the design uses documented interfaces only. Runtime capture still happens only in a replica environment with no instrument attached (P0); REA never captures traffic itself and only reads a capture file it is given. Source code is still read with ordinary tools, not REA, so RheoTool (testbed C) goes through source reading and the rheometer's control software (testbed B, plan.md 14-21) is REA's first real target.

Not settled, and recommendations only (plan.md 14-22): units for bandwidth (`B/s`, `bit/s`, `B`) and an information dimension in `contracts/units.json`; grade rows in `contracts/grades.json` for a value read from a binary and for a value measured from a capture file; how a capture of the real link is obtained without the Meta-Agent reaching the instrument (the person captures and drops the file, or the vendor's offline or simulator mode is used); and, when a request needs them, Frida's native module, TShark and capinfos, and sigrok-cli in `tools.lock.json`.
